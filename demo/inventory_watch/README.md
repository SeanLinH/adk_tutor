# 📦 多平台庫存異常監控日報

> 官網 / 蝦皮 / momo / 門市的庫存快照 → **純 Python 規則引擎**算出異常 →
> agent 判讀「今天最該處理的三件事」→ 產出行動清單與補貨草稿。

```bash
uv run streamlit run demo/inventory_watch/app.py
```

## 這在解什麼問題

多平台賣家每天早上都在做同一件事：把幾個後台的數字撈出來、在 Excel 裡對一遍、
找出「哪個要補貨、哪個賣超了、哪個平台的數量又跟倉庫兜不攏」。這件事**不難，
但每天都要做**，而且做到第 20 分鐘時人會開始漏看。

漏看的代價很具體：賣超要跟客人道歉、斷貨那幾天的自然流量全部浪費、呆料一放
半年就是幾十萬現金卡在架上。

## ADK 設計邏輯

### 架構

```
load_snapshot()          30 個 SKU × 4 個平台的今日快照
        ↓
detect_anomalies()       ← 純 Python：賣超 / 數量不一致 / 斷貨風險 / 呆滯 / 過高
        ↓                  （預設 seed 42 會得到 12 條異常，依嚴重度與影響金額排序）
digest(top_n=12)         壓成一段文字：只送前 N 條，而且數字都算好了
        ↓
   report_agent          判讀：今天最該處理的三件事，為什麼
        ↓  output_key="daily_report"
   action_agent          FunctionTool：get_sku_detail / draft_restock_order
        ↓  output_key="action_plan"
   可下載的 Markdown 日報
```

### 這個應用真正的設計決定：分界線畫在哪

整個 `warehouse.py` 裡**沒有一行 LLM 程式碼**。可售天數、缺口幾件、成本壓住
多少錢——這些全是算術。算術交給 Python 有三個好處：

| | Python 算 | 交給 LLM 算 |
|---|---|---|
| 答案一致性 | 同樣輸入永遠同樣輸出 | 每次可能不同 |
| 成本 | 0 | 每次都要 token |
| 出錯時 | 有 traceback、可寫單元測試 | 只能改 prompt 再試一次 |

那 LLM 做什麼？做 Excel 做不到的那件事：**在十幾條異常裡判斷今天先做哪三條，
並且說得出理由**。這是排序與取捨，不是計算。

`report_agent` 的 instruction 裡因此有一條硬規定：
「**只能用清單上出現的數字，不要自己算新的**」。

### 送進模型的是結論，不是資料庫

`build_request()` 送出去的是「12 條異常、預估影響 NT$ 214,672、前幾條長這樣」，
不是 30 個 SKU 的完整明細。兩個理由：

1. **每個 token 都要錢**，把整個資料庫倒進去很快就會撞上 context 上限。
2. **雜訊會稀釋判斷品質**。模型讀 30 個 SKU 的完整明細再自己找異常，準確率
   遠低於讀十幾行已經標好嚴重度與影響金額的結論。

那模型需要細節時怎麼辦？用工具查。`action_agent` 有 `get_sku_detail`，
而且 instruction 明確要求它「不要憑日報的敘述就下單，先查一次實際數字」——
這是刻意設計的**二次確認**，因為日報是模型自己寫的，讓它拿自己的輸出當事實
去做採購決策，是幻覺最容易造成金錢損失的地方。

### 用到的 ADK 元件

| 元件 | 在這裡的角色 |
|---|---|
| `SequentialAgent` | 判讀 → 行動的兩段流程 |
| `FunctionTool` | `get_sku_detail`（查證）、`draft_restock_order`（開草稿） |
| `output_key` + `{daily_report}` | 把日報注入下一段的 prompt |
| `BurstRateLimiter` Plugin | 令牌桶限流，見 `demo/common.py` |
| `RunConfig(streaming_mode=SSE)` | 日報逐字長出來，不是等 20 秒才整段跳出 |

工具函式的參數只放**模型決定得了的東西**（SKU 編號、數量），資料本身透過
`set_current_snapshot()` 從 Python 這側傳進去。不要把整份快照當成工具參數
讓模型複述一遍——那等於用最貴的方式做資料搬運。

## 怎麼看畫面

- 上方五個數字與兩個分頁，**在你按下按鈕之前就已經算好了**。這一區完全不用
  模型，也不花任何費用——先看看沒有 AI 的版本能做到什麼程度，是評估「這裡真的
  需要 agent 嗎」的好習慣。
- 換一個「隨機種子」會得到一組完全不同的異常組合，適合觀察 agent 的判讀會不會
  跟著變（好的判讀應該要變）。
- 「送給模型的異常條數」調到 5 跟調到 20，日報的品質差別很值得比較。

## 已知限制

- **假資料**：`load_snapshot()` 是亂數產生的。接真實系統時，把它換成打你的
  ERP / 平台 API，`detect_anomalies()` 以下完全不用改。
- **規則是寫死的**：安全庫存 = 10 天銷量、可售天數 < 7 天算風險——這些門檻
  該由營運自己定，不是通則。它們刻意寫成常數而不是 prompt，就是為了讓人能改。
- **補貨單只是草稿**：`draft_restock_order()` 回傳 `status: "草稿，尚未送出"`。
  真的要送出採購單，建議照 `demo/support_triage/` 的做法加一道人工核准。

## 可以往下加的東西

- **排程執行**：這個應用最自然的形態其實是「每天早上 8 點自己跑完、把日報
  寄到 LINE」，而不是有人打開網頁。實作軌 Day 24（ambient agents）談的就是這件事。
- **趨勢比較**：目前只看今天的快照。存下每天的 anomalies，就能做「這條異常
  已經連續 5 天沒處理」的升級提醒。
- **接真實平台**：蝦皮/momo 都有開放 API，可寫成 `providers/` 風格的介面。
