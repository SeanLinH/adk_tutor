當 AI 從「回答問題」進化到「完成任務」，開發者需要的不只是 API，而是一套架構思維。Google ADK 提供了完整的 Agent 開發框架，從單一 Agent 的工具呼叫，到多 Agent 之間的分工協作，本次分享將結合實戰經驗，帶你看懂 ADK 的核心設計，以及 Multi-Agent 系統的真實樣貌。

### ② 什麼是 AI Agent（約 5 分鐘）

**目標：** 用最直覺的方式讓非技術聽眾也能理解

- Agent = 能感知環境、做決策、採取行動的 AI 系統
- 跟一般 LLM 呼叫的差異：有記憶、有工具、有目標
- 類比說明：從「問問題的助理」→「能完成任務的員工」

---

### ③ Google ADK 核心模組（約 15 ~ 20 分鐘）⭐ 重頭戲

**目標：** 由小到大堆疊概念，讓聽眾跟著建立系統架構的畫面

#### Layer 1：單一 Agent 的組成

| 模組 | 說明 |
|------|------|
| **Agent** | 基本執行單位，有角色定義與任務目標 |
| **Tool** | Agent 的手腳，呼叫外部 API、查資料、執行動作 |
| **Model** | 背後接哪個 LLM（Gemini / 其他） |
| **Plugin** | ADK 內建的擴充機制，透過 Callback Hook 注入 Agent 執行生命週期的各個階段（如 before_model、after_tool 等），一次註冊、全域生效。常見用途：日誌、安全政策、監控、快取、Response 修改等 |

#### Layer 2：Agent 怎麼跑起來

| 模組 | 說明 |
|------|------|
| **Runner** | 負責執行 Agent 的引擎，管理執行流程；Plugin 也在此處統一註冊 |
| **Session** | 維持對話狀態與上下文 |
| **Memory** | 讓 Agent 記住跨輪次的資訊 |
| **Artifact** | Agent 系統內部的「檔案系統」，用於儲存、版本管理、跨 Agent 傳遞的二進位資料（如 PDF、圖片、音訊等）。以 `types.Part` 表示，支援 Session 範圍（僅當次）或 User 範圍（`user:` 前綴，跨 Session 持久），後端可選 InMemory 或 GCS |

#### Layer 3：多 Agent 架構

**核心問題：多個 Agent 之間怎麼合作？**

---

##### 🏭 Orchestration — 訂單處理流程

> 任務流程明確、由上而下、Master 統一指揮

```
訂單進來
    ↓
Master Agent（決策中樞）
  ↙       ↓       ↘
庫存     物流     客服
Agent   Agent   Agent
```

- **Master Agent** 負責拆解任務、決定順序、分派工作
- 每個 Sub-Agent 各司其職，不需要彼此溝通
- 適合：**流程固定、有順序依賴、需要高控制的場景**

---

##### 🎮 Coordination — RPG 遊戲開發團隊

> 共同目標驅動、橫向協作、Agent 自主補位

```
PM Agent：「我們要做一款 RPG 遊戲」
              ↓ 共享目標
Data Engineer ←→ SA ←→ Software Engineer
        ↘          ↑          ↙
              PM Agent
           （持續對焦目標）
```

- **PM Agent** 設定目標，不下指令
- 各專家 Agent 根據目標互相協調、補充、修正
- 適合：**任務複雜、需要多專家視角、結果開放的場景**

---

##### 架構選擇決策框架

| 情境 | 建議架構 |
|------|---------|
| 任務流程固定、有明確順序 | ✅ Orchestration |
| 任務需要多方判斷、結果開放 | ✅ Coordination |
| 需要快速、可預期的輸出 | ✅ Orchestration |
| 需要創意、多角度分析 | ✅ Coordination |

## 簡報製作重點

- **每張投影片一個概念**，不塞太多文字
- Layer 1 → 2 → 3 做成**遞進式視覺**，每層加一個模組
- Orchestration / Coordination 各用一張圖示清楚對比
- 決策框架做成**表格或對比圖**，讓聽眾可以拍照帶走
- 實戰心得用**條列 + 關鍵字**，不長篇大論
